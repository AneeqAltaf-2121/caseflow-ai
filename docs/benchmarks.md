# Performance benchmarking

`scripts/benchmark.py` measures latency of the retrieval pipeline —
semantic, keyword, hybrid, and reranked search — against a synthetic
in-process corpus. No live deployment or Docker is required; it builds
its own in-memory SQLite database and seeds it directly through the
same repository/service layer the API uses.

```bash
python scripts/benchmark.py                                    # defaults: 300 chunks, 6 queries, 5 iterations
python scripts/benchmark.py --chunks 1000 --queries 20 --iterations 10
python scripts/benchmark.py --output results.json               # also write the raw numbers as JSON
```

## What this does and doesn't measure

This runs against an in-memory SQLite database and
`LocalEmbeddingProvider` (see ADR 007) — the same dev/test stand-ins
`apps/api/tests/` uses, not the real PostgreSQL+pgvector path a
production deployment takes.
`app/repositories/chunk_repository.py`'s semantic search falls back to
a pure-Python cosine-distance scan on any non-PostgreSQL dialect,
which is *slower* than pgvector's native operator for large corpora
and *faster* to set up here than standing up real Postgres.

**These numbers are useful for one thing: catching a relative
regression between two runs of this script** — e.g. before/after a
retrieval code change — never as an absolute production SLA. No
absolute numbers from this script are recorded anywhere as a target or
guarantee.

## A regression this script actually found

Running it for the first time surfaced a real issue: `hybrid_search`'s
cache hit path (Phase 33) was *slower* than recomputing the search
from scratch.

```
operation                    n    mean ms  median ms    p95 ms    max ms
------------------------------------------------------------------------
hybrid_search_uncached       6     12.802     12.612    15.177    15.177
hybrid_search_cached         6     52.224     51.592    56.165    56.165
```

The cause: `HybridSearchService._rehydrate` re-fetched every cached
chunk with its own `get_by_id_with_document` query — an N+1 query
pattern where a ~20-result cache hit issued 20 sequential DB round
trips, more total work than the uncached path's two bulk queries
(`search_by_embedding` and `list_for_project`). A cache whose hit path
costs more than its miss path defeats the point of caching at all.

Fixed by adding `DocumentChunkRepository.get_many_by_ids_with_document`
(one batched `WHERE id IN (...)` query) and rehydrating from that
instead. Re-running the same benchmark after the fix:

```
operation                    n    mean ms  median ms    p95 ms    max ms
------------------------------------------------------------------------
hybrid_search_uncached      30     70.409      70.88   167.695   197.321
hybrid_search_cached        30      9.562      9.046    13.079    13.108
```

Cache hits are now consistently faster than a full recompute, as
intended. See `apps/api/tests/test_hybrid_search_cache.py`'s
`test_cache_hit_rehydrates_with_one_batched_query_not_one_per_chunk`
for the regression test locking this in, and
`apps/api/app/services/hybrid_search_service.py`'s `_rehydrate` for
the fix itself.

## Corpus

`num_chunks` synthetic passages are generated by combining a small
pool of subject/predicate fragments (contract-flavored, so BM25 and
the phrase-overlap reranker have realistic keyword overlap to
discriminate on), embedded in batches of 100 via
`LocalEmbeddingProvider`, and bulk-inserted. `num_queries` is drawn
from a fixed set of six realistic questions, cycled to reach the
requested count, each run `iterations` times.
